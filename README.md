# Deskwarden

A small native macOS menu bar app for a Bitwarden vault. It does two things:

- **SSH agent**: serves the SSH keys in your vault to `ssh` and `git`.
- **Secrets socket**: lets external applications read vault items by path, e.g. `Infra/Postgres`, after Touch ID. A [varlock](https://varlock.dev) plugin is included.

It isn't a full Bitwarden client and isn't affiliated with Bitwarden, Inc.

## Building

Needs Xcode 16+ (Swift 6) on macOS 15+, and `rustup` for the Bitwarden SDK.

```bash
./scripts/bundle.sh && open build/Deskwarden.app
```

`bundle.sh` builds the SDK first if `Vendor/BitwardenSdk` is missing, then signs with your Developer ID or Apple Development identity if there is one. Use a stable identity: the application keys and the Bitwarden session sit in the login keychain under the app's signature, so an ad hoc build asks for keychain access again after every rebuild.

By default the app gets a drawn icon and an SF Symbol in the menu bar. For Bitwarden's own app icon and shield, run `./scripts/fetch-bitwarden-icons.sh` before `bundle.sh`: it puts them in `Branding/`, which is gitignored because Bitwarden's trademark guidelines don't let third-party software ship its logos.

```bash
swift build
swift test
```

Without `Vendor/BitwardenSdk`, the package only has the socket library, the harness and their tests, so the plugin's tests don't need the Rust build.

The integration tests register throwaway accounts on a local Vaultwarden (Docker), add items the way another client would, then log in, sync, read, lock, unlock, relaunch and log out:

```bash
./scripts/vaultwarden.sh start
DESKWARDEN_TEST_SERVER=http://127.0.0.1:8222 swift test
./scripts/vaultwarden.sh stop
```

They use their own keychain service (`io.github.grievouz.deskwarden.tests`) and a temporary directory, so they don't touch a real account.

The varlock plugin:

```bash
cd plugins/varlock
pnpm install
pnpm test   # builds dist/plugin.cjs and runs the client and varlock e2e tests
```

The Bitwarden SDK (Rust, about 1.5 minutes on Apple silicon, needs `rustup`):

```bash
./scripts/build-bitwarden-sdk.sh
```

It checks out [bitwarden/sdk-internal](https://github.com/bitwarden/sdk-internal) at a pinned commit into `.local/`, builds `bitwarden-uniffi` for `aarch64-apple-darwin`, and writes a local Swift package with the xcframework and generated bindings to `Vendor/BitwardenSdk`. Bitwarden only publishes an iOS build of that package.

## Bitwarden account

Log in under **Account** in Settings, on bitwarden.com, bitwarden.eu or a self-hosted Bitwarden or Vaultwarden server.

- **Two-step login** works with an authenticator app or an email code. Duo, YubiKey and passkeys need a browser and aren't supported. **Remember this Mac** skips the step next time.
- **New devices**: Bitwarden may email a verification code the first time Deskwarden logs in.
- **The master password never leaves the Mac.** The SDK derives the master key (PBKDF2 or Argon2id) and the server only gets a hash of it, as with the official clients.
- **Identity**: Deskwarden presents itself as a macOS desktop client (`client_id=desktop`, device type 7) with a stable device id, so it appears in your account's devices as "macos".

**Unlocking** happens with Touch ID when Deskwarden opens, and from **Unlock with Touch ID** in the menu. The master password is only needed to log in, and again if Touch ID can't be used (fingerprints changed, Touch ID unavailable, or you choose **Use Master Password** in the prompt); unlocking with it sets Touch ID up again. Behind it, the vault's user key is sealed with a Secure Enclave key that only works after Touch ID with the fingerprints enrolled at the time (ECIES with P-256, HKDF-SHA256 and AES-GCM, via CryptoKit; no keychain entitlement needed), and the SDK unlocks with the key Touch ID opens.

**While unlocked**, the SDK holds the user key in memory. Item names and folders are decrypted to build the path index; values are decrypted only when a client asks for one.

**On disk**, everything is either public or encrypted, like the official clients' local data:

- `~/Library/Application Support/Deskwarden/account.json`: KDF settings and the encrypted user and private keys, so the vault can be unlocked again.
- `~/Library/Application Support/Deskwarden/vault.json`: the last sync, still encrypted, so unlocking works offline.
- `~/Library/Application Support/Deskwarden/touch-id.json`: the user key sealed for Touch ID, and the Secure Enclave key in the form only this Mac's enclave can use.
- The refresh token, in the login keychain.

**Syncing** happens after logging in and unlocking, after the Mac wakes, and on **Sync Now**. Every minute Deskwarden asks the server for the vault's revision date and syncs only if it changed. Each sync also refreshes the stored key material, so a password or KDF change on another device keeps working.

**Lock** drops the keys from memory and forgets Touch ID approvals. **Log Out** also deletes the stored account, the cached vault, the Touch ID key and the session. If the session is revoked (password changed elsewhere, sessions deauthorized), Deskwarden logs out.

## SSH agent

Turn on **SSH agent** in Settings; it's off by default. Turning it on adds this block to the end of `~/.ssh/config` (creating the file if needed), and turning it off removes it again:

```
# Added by Deskwarden. Turning off its SSH agent removes this.
Host *
  IdentityAgent ~/.deskwarden/ssh-agent.sock
# End of Deskwarden
```

`IdentityAgent` reaches every `ssh` run, including from apps opened in the Dock, which don't see a shell's `SSH_AUTH_SOCK`, and it takes precedence over `SSH_AUTH_SOCK` for `ssh`. Being at the end, an `IdentityAgent` you set for specific hosts earlier in the file still wins. A symlinked `~/.ssh/config` is written through, not replaced. Tools that talk to the agent directly only read `SSH_AUTH_SOCK`: `ssh-add`, and git's SSH commit signing (`gpg.format ssh`), which signs through `ssh-keygen`. For them, also export it in your shell, e.g. in fish:

```fish
set -gx SSH_AUTH_SOCK "$HOME/.deskwarden/ssh-agent.sock"
```

Shells started inside tmux or herdr pick this up too, since their shell config runs again.

The agent serves the vault's SSH key items: Ed25519, ECDSA (P-256, P-384, P-521) and RSA, with SHA-2 signatures for RSA when the client asks for them, which current OpenSSH always does. `ssh-add -L` lists them, named after their vault items.

- **Listing keys** never asks, unless the vault is locked: then one Touch ID prompt unlocks it.
- **Signing** follows **Verify requests**, like the secrets socket.
- **First use**: an app's first signature always asks ("let Alacritty use your SSH key “GitHub” (git → ssh)") and adds the app to **External Applications** as an SSH client. Removing it there means it's asked about again next time.
- **Refusing** ends that connection's requests, so a client can't keep prompting by offering one key after another.

**Who's asking.** SSH clients can't present a key, so they're identified by their process. The agent asks the kernel which process connected and checks it belongs to you. The connecting process is almost always `ssh`, so the agent walks up its parents to the app it was started from: the outermost `.app` bundle, such as your terminal or editor, or the topmost process below launchd when there's none (a tmux server, for example). An app signed by a developer is recognized by team and bundle identifier; anything else by its path and code hash, so an unsigned app is asked about again after it changes.

Anything running inside an approved app counts as that app, as with every SSH agent; the Touch ID prompts are what stop it from signing silently. The agent never hands out private keys: each one is decrypted only to make the signature at hand.

Adding keys to the agent, agent locking and extensions such as `session-bind@openssh.com` aren't supported; clients carry on without them.

## Using it with varlock

1. In Deskwarden's Settings, under **External Applications**, click **Add Application…**, name it, and copy the key (`dwk_…`). It's shown once.
2. Make it available to varlock without committing it, e.g. `set -Ux DESKWARDEN_KEY dwk_…` in fish, or a gitignored `.env.local`.
3. In `.env.schema`:

```env-spec
# @plugin(../deskwarden/plugins/varlock/dist/plugin.cjs)
# @initDeskwarden(key=$DESKWARDEN_KEY)
# ---
# @type=deskwardenKey
DESKWARDEN_KEY=

DB_PASSWORD=deskwarden("Infra/Postgres")
DB_USER=deskwarden("Infra/Postgres", field=username)
STRIPE_KEY=deskwarden("Stripe")
```

Paths are `Folder/Item name` (nested folders are `Parent/Child/Item name`), just `Item name` when the name is unique, or an item id. `field` is `password` (default), `username`, `notes`, or any custom field name, matched case-insensitively. Two items matching the same path is an error, never a guess.

`@initDeskwarden` also takes `socketPath=` (default `~/.deskwarden/secrets.sock`) and `id=` for more than one instance, used as `deskwarden(id, "Path")`.

## Secrets socket protocol

The socket is `~/.deskwarden/secrets.sock`, in a `0700` directory, chmodded `0600`.

**Transport.** TLS 1.2 with `TLS_ECDHE_PSK_WITH_CHACHA20_POLY1305_SHA256` (`ECDHE-PSK-CHACHA20-POLY1305` in OpenSSL). Every external application's key is registered as a pre-shared key, identity = key id and key = the 32-byte secret, so only a client holding a key can complete the handshake, and ephemeral ECDH gives each connection forward secrecy. It's TLS 1.2 because Node can't do TLS 1.3 with external PSKs. Both sides use only their platform's TLS stack (Network.framework, Node's `tls`).

**Key format.** `dwk_<id>_<secret>`: `id` is 16 hex characters, `secret` is 32 bytes in unpadded base64url.

**Framing.** Each message is a JSON object, sent as a 4-byte big-endian length followed by the UTF-8 payload, at most 1 MiB. Binary fields are standard base64.

**Handshake.** Network.framework doesn't tell the server which PSK a client used, so the client also proves which key it holds:

```
server → { "type": "challenge", "version": 1, "nonce": <32 random bytes> }
client → { "type": "auth", "keyId": "…", "proof": HMAC-SHA256(secret, "deskwarden-auth-v1" ‖ nonce),
           "client": { "name": "varlock", "pid": 123, "cwd": "/path" } }
server → { "type": "ready" }    or an error, then the server closes the connection
```

The Touch ID prompt names the application as you registered it. `client` is self-reported and only adds context, such as the working directory.

**Requests.** Any number of `get`s over one connection, answered by `id`:

```
client → { "type": "get", "id": "1", "path": "Infra/Postgres", "field": "password" }
server → { "type": "value", "id": "1", "value": "…" }
server → { "type": "error", "id": "1", "code": "not_found", "message": "…" }
```

Error codes: `bad_request`, `unauthorized`, `locked`, `denied`, `not_found`, `ambiguous`, `field_not_found`.

**Verification.** **Verify requests** in Settings decides how often a request needs Touch ID (falling back to the account password):

- **Every request**: every `get` and every SSH signature.
- **First request per unlock** (default): the first request from each application after the vault unlocks; it isn't asked again until the vault locks.
- **Every 5 / 15 / 60 minutes**: once per application, then not again until the time has passed.
- **Never**: no prompt.

Denying a prompt denies the rest of that connection's requests.

**Locked vault.** A request that arrives while the vault is locked asks for Touch ID to unlock it ("unlock your vault so varlock in shop can read Infra/Stripe"), and that prompt also counts as verifying the request. Requests arriving together share the prompt. If it's dismissed, or Touch ID isn't set up yet, the request fails with `locked`, and so does the rest of that connection.

## Security model

What the socket protects against:

- other users on the Mac (socket permissions, and they'd still need a key);
- processes that find the socket but have no key: they can't complete TLS;
- eavesdropping on the socket, including if it's ever forwarded or mounted into a container.

What it doesn't:

- malware running as you can read wherever you keep the key and connect. Touch ID is the gate there, except that a stolen key can ride an approval that's still valid (within the interval), and with **Never** there's no gate at all.
- root.

Planned for the secrets socket: verify the requesting process from the kernel, as the SSH agent does, so approvals can be scoped to one terminal session and the prompt can name the real executable. Network.framework doesn't expose a connection's socket, so this needs either matching sockets through `proc_pidfdinfo` or moving to a raw socket server.

## Roadmap

1. **Lock after a period of inactivity.**
2. **Per-app verification settings**, e.g. every SSH signature but only the first secret of each varlock run.
3. **Kernel-verified clients on the secrets socket too**, like the SSH agent, so approvals can be scoped to one terminal session.

The official [iOS app](https://github.com/bitwarden/ios) is the reference for Bitwarden's API: its request fields, error handling and SDK record mapping are what `DeskwardenAccount` follows.
